# 武器独立显示与资源操作一致性修复设计

日期：2026-09-04

## 背景与目标

当前项目存在两类相互关联的问题：

1. 装备一把仙斧后，背包中所有同道具 ID 的备用仙斧都会被显示为“已装备”。
2. 合成等异步资源操作在数据库响应前可以被重复触发，多个请求会读取同一份旧库存，造成重复扣除、重复发奖或材料不足仍合成成功。

本次修复目标是让背包中的每把武器按独立物品处理，并让所有会增加、扣除或兑换玩家资源的点击操作在页面内不可并发。合成操作还需要数据库级原子校验，确保多个页面同时操作时也不会透支材料。

## 已确认的游戏规则

- 当前装备的仙斧不占背包格，装备时从背包扣除，替换下来的旧仙斧放回背包。
- 背包里即使出现与当前装备相同道具 ID 的仙斧，也都是独立的备用武器。
- 备用仙斧可正常显示“装备”和“出售”按钮。
- 当前仙斧没有随机词条、强化等级或耐久等个体属性，因此库存仍可按道具 ID 和数量聚合存储；界面将聚合数量展开成多个独立格子。
- 将来加入个体属性时，再迁移为带唯一实例 ID 的武器数据结构。本次不提前引入该改造。

## 方案选择

采用“统一页面操作锁 + 合成数据库原子事务”的混合方案。

只做按钮禁用无法防止多标签页或直接并发请求；把所有经济操作一次性改造成服务端事务则改动范围过大。混合方案优先彻底保护已经复现的严重合成漏洞，同时为其他资源按钮提供一致的页面内防连点保护，并为后续逐步服务端化保留统一入口。

## 设计

### 1. 武器显示与操作

- 背包格不再通过 `Game.state.axeId === itemId` 判断是否装备。
- 从背包打开任意仙斧详情时，只按仙阶限制决定能否装备；不会因为当前装备具有相同 ID 而显示“已装备”。
- 出售背包仙斧时不再按当前装备 ID 拒绝。出售对象始终是背包中的一个备用数量，不会影响装备栏中的仙斧。
- 装备同 ID 仙斧时允许交换：旧装备先回到背包，新选中的备用仙斧再从背包取出。因为两者 ID 相同，最终背包数量不变，装备状态保持正确。
- 装备、出售必须检查库存扣除结果，失败时不更新装备或游戏币，也不显示成功。

### 2. 通用页面操作锁

增加一个统一的异步操作保护入口。每类操作使用稳定的业务键，例如 `compose:<itemId>`、`mail:<mailId>` 或 `shop:<shopId>`。

- 操作开始时同步占用锁，后续相同操作直接返回，不再发送请求。
- 对应按钮立即禁用，文字改为“处理中”或该操作的具体进行中状态。
- 操作成功、失败或抛出异常时都在 `finally` 中释放锁。
- 失败时恢复按钮并显示明确错误，不显示成功提示。
- 锁覆盖玩家端所有会改变资源或领取状态的入口：合成、道具兑现、装备、出售、商店购买、提现申请、签到里程碑、成就、任务、自主任务、主题额外奖励和邮件奖励。
- 管理端提现通过或驳回也使用相同的防重复机制，防止一次审核被提交多次。

页面操作锁负责解决一次页面中的快速连点和误操作，但不被视为数据库安全边界。

### 3. 合成数据库原子操作

在 Supabase 中新增合成 RPC。一次数据库事务完成以下步骤：

1. 校验参数是正整数，并限制单次合成数量。
2. 锁定玩家对应的材料库存记录。
3. 根据数据库中的实时数量检查材料是否足够。
4. 扣除材料；数量归零时删除库存记录。
5. 增加成品库存；已有记录则累加，没有则插入。
6. 返回扣除后的材料数量和增加后的成品数量。

任一步失败，整笔事务回滚，不会出现只扣材料或只发成品。道具类型、合成配方和单次上限仍由页面配置决定，但 RPC 接收并验证具体材料 ID、成品 ID、扣除数和发放数；数据库库存是数量判断的唯一依据。

当前项目使用公开匿名连接且未启用 RLS，因此本次 RPC 的重点是事务一致性和防并发透支，而不是防止恶意调用。账号认证和 RLS 属于后续独立的安全改造。

### 4. 合成速度优化

现有一次合成会串行执行材料查询、材料写入、成品查询、成品写入、玩家状态刷新和背包刷新，数据库又部署在悉尼，因此约六次网络往返会累积为明显延迟。

修改后：

- 扣材料和发成品合并为一次 RPC 网络请求。
- RPC 成功后使用返回值更新本地背包，不再为合成执行完整玩家状态刷新。
- 如本地数据无法可靠更新，则只补充一次背包查询，不刷新无关玩家数据。

正常情况下合成从约六次串行请求减少到一次；降级同步时最多两次。

### 5. 其他资源操作审计和加固

审计发现，合成之外的道具兑现、装备、出售、签到/成就/任务/邮件领奖、商店购买、提现与管理员审核也缺少统一并发保护。部分领取流程先发奖励再标记已领取，快速连点存在同类风险。

本次处理原则：

- 所有上述入口先接入统一页面操作锁并检查每个数据库调用的返回结果。
- 对已有状态字段的领取操作，状态更新必须带“当前仍未领取/仍待处理”的条件；未成功占用领取资格时不得发奖。
- 邮件和任务等奖励流程若现有表结构无法在一次条件更新中可靠占用资格，则先将状态原子地改为处理中或已领取，再发放奖励；发放失败时记录错误并重新同步，避免重复发奖优先于自动重试。
- 涉及多个表且无法用现有条件更新保证一致性的操作，在测试中确认风险后补充小型 RPC，不通过更多页面状态判断掩盖问题。

## 错误处理

- 数据库返回失败时，业务方法必须返回失败，调用方不得继续后续发奖或更新余额。
- 合成材料不足时提示实际不足，不关闭合成窗口，并刷新背包数量。
- 网络异常时提示“操作未完成，请重试”，解除页面锁并恢复按钮。
- 不确定操作是否成功时，以重新读取数据库后的结果为准，不根据本地旧状态补发资源。
- 所有异常记录到浏览器控制台，包含操作类型和业务 ID，便于后续排查。

## 测试与验收

### 武器

- 装备某 ID 仙斧后，背包中同 ID 的每个备用格均显示“装备”和“出售”。
- 装备同 ID 备用仙斧后，背包数量不变。
- 出售同 ID 备用仙斧后，背包数量减一、游戏币只增加一次，当前装备不变。
- 库存扣除失败时不改变装备、库存或游戏币。

### 合成

- 材料恰好够一次时连续快速点击，只成功一次。
- 材料不足时不会生成成品。
- 两个页面同时提交只有库存允许的请求成功，不会出现负库存或超额成品。
- 成功、失败和断网后按钮状态都能正确恢复。
- 记录合成前后的请求次数与耗时，确认正常路径不超过一次 RPC；需要同步时不超过两次请求。

### 其他操作

- 对兑现、装备、出售、购买、提现和所有领奖按钮执行快速连续点击测试。
- 每个操作只能产生一次资源变化或一次状态变化。
- 管理员重复点击通过或驳回不会重复付款、退款或发送邮件。
- 失败响应不会显示成功提示，页面重新同步后与数据库一致。

## 发布

- 先在 Supabase 安装并验证 RPC，再发布调用新 RPC 的前端代码，避免正式页面先引用不存在的数据库函数。
- 数据库变更保留可重复执行的 SQL 文件并记录在项目中。
- 本地测试和浏览器验收通过后提交并推送 GitHub，由现有正式发布流程上线。
