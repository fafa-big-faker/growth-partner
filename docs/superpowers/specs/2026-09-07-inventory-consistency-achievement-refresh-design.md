# 库存一致性、即时刷新与成就红点设计

## 目标

修复同一道具出现多个背包格子、部分数量无法使用、消耗或获得后界面延迟更新，以及成就存在可领取奖励时红点未持续显示的问题。

## 已确认约束

- 允许通过数据库迁移合并测试账号现有的重复库存记录。
- 同一账号、同一道具 ID 的重复数量相加后保留为一条记录，例如 `22 + 2 = 24`。
- 不清空或重置其他玩家数据。
- 普通可堆叠道具必须按道具 ID 显示为一个格子；武器继续按独立实例保存和展示。
- 数据库写入成功后，当前可见界面的数量和红点必须立即更新，不等待下一轮远程查询。
- 不执行浏览器视觉验收，除非用户另行要求。

## 根因

### 重复道具格子

当前库存表没有可靠保证 `(user_role, item_id)` 唯一。普通道具发放使用“先查询、再插入或更新”的非原子流程；当任务奖励或其他发放同时发生时，多个请求可能都判断记录不存在并各自插入一行。

库存读取把数据库的每一行直接映射为一个背包格子，而合成与锻造 RPC 只选择同一道具中的一行进行扣除。这会造成同一道具显示多个格子，并出现剩余记录看得见但不参与预期扣除的现象。该问题不是新旧道具 ID 不一致导致的。

### 数量刷新延迟

合成和锻造成功后只更新部分本地状态或局部页面。背包、锻造入口、已打开的锻造面板和其他数量消费者没有通过统一入口同步，因此需要等待后续完整刷新才显示新数量。

### 成就红点

可领取判断本身使用“已达成且未领取”的规则，但配置中的成就 ID 与历史领取记录可能存在数字和字符串类型差异；同时部分会改变成就进度的操作没有在成功后统一刷新红点。这两种情况都会导致红点与实际领取状态不一致。

## 方案选择

### 采用：数据库约束、原子操作与前端防御性同步

这是唯一能同时修复现有数据、阻止再次产生重复数据，并保证界面即时一致的方案。

- 数据库迁移先按账号和道具 ID 汇总数量，再删除多余行并建立唯一约束。
- 普通道具发放改为数据库原子操作，避免并发请求再次插入重复行。
- 所有消耗型 RPC 使用唯一库存行，并保持数量校验、扣除和结果发放在同一事务中。
- 前端读取仍按账号和道具 ID 聚合，作为历史数据或迁移异常的最后一道保护。
- 成功操作统一触发库存状态和成就状态的局部同步。

### 未采用：只在前端合并显示

虽然能隐藏重复格子，但数据库仍存在多行，合成和锻造仍可能只扣除其中一行，无法解决“看得到却用不了”。

### 未采用：只清理数据库

能解决当前重复数据，但不能消除非原子发放的并发风险，也不能解决页面数量和红点延迟更新。

## 详细设计

### 1. 库存数据迁移

新增版本化、可重复执行的迁移脚本：

1. 对普通库存按 `(user_role, item_id)` 分组。
2. 将每组数量求和并写入一条保留记录。
3. 删除该组其余重复记录。
4. 为 `(user_role, item_id)` 添加唯一约束或唯一索引。
5. 新增原子增加道具 RPC，使用冲突更新累加数量。
6. 更新合成、锻造、签到等库存 RPC，使其只依赖唯一记录并继续进行事务内数量校验。

迁移不处理独立武器实例表，也不删除任何有效数量。

### 2. 前端库存模型

`DB.getInventory()` 在返回游戏层前按规范化后的道具 ID 汇总数量。即使远端意外存在重复行，游戏层也只会获得一个道具条目。

普通道具发放统一调用原子增加道具 RPC，不再执行“查询后决定插入或更新”。扣除和合成、锻造继续由数据库 RPC 原子完成，前端不预先伪造成功结果。

### 3. 即时数量同步

新增共享的库存变更同步入口。数据库操作成功并返回最新库存后，一次性完成：

- 替换 `Game.inventory`。
- 同步背包“新”标记的数量快照。
- 若背包当前可见，局部重绘对应格子和数量。
- 更新修仙页的锻造入口材料数量。
- 若锻造面板已打开，更新 `当前数量/单次消耗` 和按钮可用状态。
- 更新其他当前可见的库存数量消费者。
- 重算成就红点。

合成成功提示只在数据库完成并且本地状态已同步后展示，保证玩家看到“已合成”时结果道具已经出现在当前界面。锻造扣除也遵循相同顺序。

### 4. 成就红点

成就 ID 在配置载入、领取记录读取和比较时统一规范化为字符串。可领取状态唯一规则为：

`当前进度 >= 达成目标 && 领取记录中不存在该成就 ID`

任何会改变成就进度或领取状态的成功操作都调用同一个红点刷新入口。红点 DOM 暂时不存在时保存计算结果，相关导航或页面重新渲染后立即应用，避免离开修仙页时的更新丢失。

## 错误与一致性

- 数据库操作失败时不修改本地库存，也不显示成功提示。
- 迁移先合并后建立唯一约束；若约束创建失败，事务整体回滚。
- 重复执行迁移不会重复累加已经合并过的数量。
- 原子发放 RPC 只接受正整数数量；扣除继续校验库存充足。
- 即时局部刷新失败时退化为一次完整库存重载，但不会重复执行奖励或消费操作。
- 成就 ID 缺失或配置无效时忽略该条并记录诊断信息，不产生永久红点。

## 测试与发布

- 库存读取：重复行聚合、不同道具隔离、零数量处理。
- 数据迁移：`22 + 2 = 24`、多账号隔离、重复执行幂等、唯一约束生效。
- 原子发放：并发增加不会生成重复行，最终数量正确。
- 合成与锻造：成功提示前本地库存已同步，入口和面板数量立即一致。
- 成就：数字/字符串 ID 一致识别；达到未领取持续红点；领取后消失；多个可领取项目领取一个后仍保留红点。
- 运行完整 Node、JavaScript、Python 和资源检查。
- 应用 Supabase 迁移后推送 `main`，确认 GitHub Pages 部署成功；不执行浏览器视觉验收。
